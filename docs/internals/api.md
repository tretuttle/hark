# Extension API and the export host

Extension pages call one API, `browser.hark`, defined by one table in `apps/extension/experiment/contract.ts`. The experiment host runs it in the parent process with the system principal. Pages hold the `moz-extension` principal and get counts, rows and job states back: no file path, body byte or HAR text crosses in either direction. Content principals reach nothing.

## One table, a parser on every parameter

- Every parameter carries its own parser, and `createHarkApi` runs `parseArguments` before any handler, in every host. Gecko's schema checks the experiment host's integers too, but the standard host's port has none, so the parser is the check that always runs. Object parameters are `any` in the generated `schema.json` and checked only by their parser: `getPopup({ tabId: -1 })` is refused by the parser, `getEnvironment(-1)` by the schema first.
- `contract.test.ts` walks every row's parameter and result types and fails typecheck when a key that holds a path, folder, text, content or HAR, or a byte array, appears at any depth. Index signatures are walked apart from named keys, because a `string` key would swallow every literal key in a union and hide a `folder.path` beneath it.
- Pages may import only `experiment/contract.ts`; a lint override on `apps/extension/src/**` refuses the rest.

## History and settings rows

- `listSites`, `listSessions`, `getSettings`, `setSettings`, `excludeSite`, `includeSite`, `chooseExportFolder` and `useDownloadsFolder` move settings and site names between the `moz-extension` principal and the system principal, both ways, through the same parsers. They carry no path: the chosen export folder reaches a page as its own name, and a refusal as a fixed word (`inside-profile`, `contains-recording`, ...) from `refusedFolder` in `settings-host.ts`.
- The folder picker runs in the parent (`nsIFilePicker` in folder mode), so a page never holds the path it chose. The folder is checked by its real path against the roots the export checks it against again when it writes; a link into the profile is refused like the profile.
- `setSettings` carries one setting by name, and the parent applies it to the settings it holds, on its write chain. A page that sent every setting from its own copy wrote an older value back when two changes overlapped. A settings change is applied only after `settings.json` holds it, through its temporary file; a failed write rejects and changes nothing. A lower body limit runs retention at once, so the archive is under it before the next start. The floor the parser raises a value to (64 MiB of bodies) is the page's smallest choice.
- `excludeSite` always deletes the site's data, so the pages ask once before they call it. `includeSite` records the site again from its next request.

## Tab ids are states

`tabManager.get` throws for tab 0, a closed tab, an unknown id and a private tab this add-on may not see. The host looks a tab up once and turns any throw into `no-such-tab`, so `getEnvironment` and `getPopup` answer every parsed id with a state. `{ tabId: null }` is the popup's own "no tab" (Zen's empty tab reports -1).

## Counts and exports read the same lines

- The activity index is filled at startup from every valid segment summary, after recovery summarized earlier runs, and then from each batch of lines the store appends. Both the popup and an export flush the store twice first: a file body's line joins a batch only after its rename, which runs on the write chain after the first flush was queued. The popup's count for a preset therefore equals the entries the export writes, live captures included.
- An export reads the segments `segmentsFor` names, keeps the lines `inSelection` accepts, and adds the recorder's live captures as in progress. Bodies are read from packs and body files in 3 MiB chunks; a stored wire encoding is undone by Gecko's own converters (`gzip`, `deflate`, `br`, `zstd`), so `content.size` is the decoded size.

## The file

- One export runs at a time, and it keeps running after the popup closes. `listExports` keeps this run's ten newest jobs.
- The file goes to the chosen folder or the browser's Downloads folder.
- **The rule:** an export never overwrites, deletes, renames or leaves bytes in a file it did not create, and never reports `done` for a file it did not write. A check of a path followed by a call on that path cannot keep it, because another process can swap the path between the two. So the export acts on objects it holds, not on paths:

  | Platform / route                       | Folder                                                                                                                                                        | The export's file                                                                                                  | Finishing                                                                                                                                                         | Failure, cancel, crash                                                                                                           |
  | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
  | Linux (unnamed link)                   | held as a directory descriptor (`O_DIRECTORY \| O_NOFOLLOW`), checked against its path (`statx`)                                                              | unnamed in the held folder (`O_TMPFILE`), written and read only through its descriptor                             | `linkat` of `/proc/self/fd/<n>` into the held folder (`EEXIST` -> `<name> (2).har`)                                                                               | closing the descriptor ends an unnamed file; nothing is renamed or deleted                                                       |
  | Linux (named part)                     | held as a directory descriptor (`O_DIRECTORY \| O_NOFOLLOW`)                                                                                                  | `<name>.har.part`, opened with `openat(..., O_CREAT \| O_EXCL \| O_NOFOLLOW)`                                      | `renameat2(..., RENAME_NOREPLACE)` inside the held folder (`EEXIST` -> `<name> (2).har`)                                                                          | `unlinkat` inside the held folder (if identity still matches)                                                                    |
  | macOS (arm64, x86-64)                  | held as a directory descriptor (`O_DIRECTORY \| O_NOFOLLOW \| O_CLOEXEC`), checked with `fstat` dev+ino                                                       | `<name>.har.part`, opened with `openat(..., O_CREAT \| O_EXCL \| O_NOFOLLOW \| O_CLOEXEC)`                         | `renameatx_np(..., RENAME_EXCL)` inside the held folder (`EEXIST` -> `<name> (2).har`)                                                                            | `unlinkat` inside the held folder (if identity still matches)                                                                    |
  | Windows                                | held via `CreateFileW` (`FILE_FLAG_BACKUP_SEMANTICS \| FILE_FLAG_OPEN_REPARSE_POINT`), checked with `GetFileInformationByHandle` volume serial and file index | `<name>.har.part`, opened via `NtCreateFile` (`FILE_CREATE`, `FILE_OPEN_REPARSE_POINT`) relative to `folderHandle` | `NtSetInformationFile(FileRenameInformation)` with `RootDirectory = folderHandle`, `ReplaceIfExists = FALSE` (`STATUS_OBJECT_NAME_COLLISION` -> `<name> (2).har`) | `SetFileInformationByHandle(FileDispositionInfoEx)` (`DELETE \| POSIX_SEMANTICS`, fallback `FileDispositionInfo`), never by path |
  | Without an atomic no-replace primitive | none                                                                                                                                                          | none                                                                                                               | refused as `no-atomic-rename` (`ENOTSUP` / `EOPNOTSUPP` / `ENOSYS`, unsupported platform, or unheld folder); never falls back to check-then-rename                | existing `<name>.har.part` is discarded via its handle/dirfd                                                                     |

  All of these calls run in `file-worker.ts`, a ChromeWorker using js-ctypes (Gecko has no unnamed-file or atomic no-replace call), so a call stuck in the kernel stalls that worker, not the main thread, and still ends the export `timed-out`. The parent script starts it from `resource://hark/`, a substitution for the add-on's own package that grants no content access. `IOUtils.move` checks before renaming and is never used.

- An export must always succeed, so on Linux the link route steps aside rather than fail. The worker checks, right after `O_TMPFILE`, that `/proc/self/fd/<n>` leads to the new file (`statx`, compared by device and inode); without `/proc`, or with it masked, no link can name the file and the export names a part instead. When the link itself fails after the file is written, because `/proc` stopped leading to it or with `EXDEV`, `EMLINK` or `EPERM` (`LINK_FALLBACK`), the whole file is copied from its descriptor, in pieces that end on whole UTF-8 sequences, into a new named part held in the same folder descriptor, which finishes with `renameat2(..., RENAME_NOREPLACE)` once its length and SHA-256, read back through its handle, equal the unnamed file's, read back through its descriptor; otherwise `copy-mismatch`. Where `/proc` cannot be read, the held folder is still checked (`statx` of the path against the descriptor, or `fstat` / `GetFileInformationByHandle` on macOS / Windows), and a held folder with no links left is gone.
- Each job keeps its route in the parent: `link`, or `named` and why (`platform`, `harness-pref`, `unnamed-refused`, `fd-link-unavailable`, `fd-link-lost`, `link-refused`) with the errno; a page sees only `link` or `named`.

- Before finishing, the file must hold the written length and first bytes, and the held folder must still be at the folder's path. After finishing, the folder must still be there, the finished name must have the same device and inode (or Windows volume serial and file index) as the held file, and the file must still hold what was written. A failure after `linkat` or atomic rename changes nothing the finish made and names no file: the job says `unconfirmed`, because no name is proven. A cancel that arrives after the export finished is reported in the job's audit. On Linux's unnamed route, a kill leaves nothing to journal or recover.
- Where a part is named, recovery deletes only a part it can prove the export created. The document's first bytes carry a random id (`log._harExportId`), and the sink writes that opening alone, at once. Only after the exclusive create succeeded and the opening is read back from the file does a line in the archive's `exports.jsonl` name the part, with those bytes as its head. An end line follows the rename, the delete, or the finding that the file at the path is no longer the export's. The next start deletes a part with no end line only when the file at its path is a regular file, not a link, that still starts with its head, checked again just before the delete; anything else is left and reported as `leave-export-part`. On POSIX, that read opens the path `O_RDWR | O_NONBLOCK` (which never waits on a FIFO) and reads nothing from a file shorter than the head.
- Every file call goes through `exportFiles` in `export-file.ts`; `geckoExportPlatform` in `host.ts` and `file-worker.ts` hold the only raw calls. For a named part:
  - The folder is checked by its real path. A folder that is a link, or whose real path is inside or contains the profile, the archive or a known substitution, is `folder-refused`, before anything is created in it. A missing folder is created, then checked again, and then opened as a held folder handle/descriptor; if holding fails with `ENOTSUP`/`ENOSYS`, the export refuses with `no-atomic-rename`.
  - The part is created exclusively inside the held folder (`create-part`) and every byte goes through that one handle, opened for reading and writing; the export never opens the part's path again, because a FIFO swapped in at that path would make the export wait forever. Before the journal line and the atomic rename, the path must still name the handle's file (`identity-at` against `identity`), and the handle must read back the written length and first bytes. Otherwise `file-replaced`.
  - After the atomic rename (`rename-part`), the folder and finished entry must still match the held folder and held file identities (`identity-at` against `identity`); otherwise the job ends `unconfirmed` (`folder-refused`, `folder-missing` or `file-replaced`) or, if caught before finishing, discards via handle/dirfd.
  - A discard deletes only via `discard-part`: `SetFileInformationByHandle(FileDispositionInfoEx)` on Windows (leaving the journal open with `discardFailed` if the kernel refuses), or `unlinkat` inside the held folder on POSIX after checking the entry's identity matches the held file.
- A refused call is the only failure. A folder that is gone, moved or replaced by the time a call fails is reported as that (`folder-missing`, `folder-refused`, `not-a-folder`), whatever the call threw; otherwise the kind comes from `ERRNO_KINDS` for the worker's errno names (and Win32 mapped errors) or `FS_ERROR_KINDS` (`ENOSPC` and `EDQUOT` are `disk-full` with no free bytes, `EIO` is `io-error`, `ENOTSUP`/`EOPNOTSUPP`/`ENOSYS` are `no-atomic-rename`). `EBADF`, `EFAULT`, `EINVAL` and `ENOMEM` are a fault in the call or the process, not the folder, and stay `other`. Each name is produced by a row of `export-failures`, for real where a file system here can produce it, and otherwise through `export-fault`, which makes the worker's next call of one kind answer an errno without running. A full disk is `disk-full` with both numbers whenever the volume had fewer free bytes than the call needed. Gecko's own Downloads helper falls back to the system Downloads folder when the configured one fails, so the matrix names each row's folder in `settings.json`.
- A failure is a fixed kind and numbers, with no text field. A platform error's message names the export folder and the profile (`jar:file://<profile>/extensions/...`), and the failure crosses to the `moz-extension` principal, so a text field would carry both to it. `contract.test.ts` fails typecheck if any failure field reachable from `listExports` is not a number or its kind is not a fixed word.
- Cancel ends the job `cancelled` at once and aborts the run's signal, which `runExport` reads before every body chunk and the finish reads before naming the file, so at most one chunk (4 MiB of base64) and one sink batch are written after it.
- Every asynchronous worker call is bounded at `EXPORT_STEP_MS`, 15 s, and a call still running then ends the export `timed-out`. A Linux link that lands after the limit names the export's own file and is left; a named part's late rename is checked and discarded (`cleanUp`).
- A harness profile can hold an export at named pauses (`export-pause` on the harness topic: `before-link`, `before-rename` and `after-link`), arm a worker errno (`export-fault`), force named parts on Linux (`extensions.hark.harness.namedParts`), override the archive location (`extensions.hark.harness.dataHome`), and read a job's route (`export-route`). On Linux, the matrix masks `/proc/<pid>/fd` inside the browser's own mount namespace with `tools/browser-harness/native/mask-proc-fd.c`, and lifts the mask as soon as the export ends: Gecko itself reopens `/proc/self/fd/<n>` to make shared memory, and aborts with `MOZ_CRASH(failed to create shared memory)` the next time its font list grows without it. A done row's file is read back and every fixture body checked against its pinned SHA-256, and a copied file against the unnamed file read through `/proc/<pid>/fd` from outside while the link waited.
